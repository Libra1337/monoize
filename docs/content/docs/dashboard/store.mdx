## Open the Store

Open **Store** at `/dashboard/store`. Select **Balance**, **Plans**, or **Redeem code**.

![Store](/images/en/store.webp)

Use the currency control to show CNY or USD. The control updates the balance, current-month usage, prices, bonuses, received amounts, and plan quotas.

Monoize refreshes the USD/CNY rate at most once every 15 minutes. It keeps the last valid rate when a refresh fails.

## Recharge balance

1. Select a recharge product or enter a custom amount.
2. Review the recharge amount, bonus, and actual received amount.
3. Select one enabled payment Channel.
4. Create the order.

Monoize saves the payment attempt before it contacts the Provider. Stripe then opens its hosted Checkout page.

Alipay submits a signed official payment form. WeChat Native shows a scannable QR code. WeChat H5 opens the official mobile payment page.

Do not create another attempt when the Provider result is unknown. Wait for Monoize to reconcile the existing attempt.

The Store checks the order every two seconds after checkout. It stops after payment and fulfillment finish, the order closes, or the order expires.

Open `/dashboard/orders` to review the order. Check the payment state and the fulfillment state separately.

Monoize grants the balance only after it verifies the provider payment. An administrator cannot mark an unpaid order as paid or fulfilled.

## Configure Stripe callbacks

Set the Stripe Webhook endpoint to `https://lynshen.org/api/store/callbacks/{channel_id}`. Replace `{channel_id}` with the Stripe Channel ID.

Subscribe to `checkout.session.completed` and `checkout.session.async_payment_succeeded`. Save the endpoint signing secret in the encrypted Stripe credential.

## Configure Alipay callbacks

Set the Alipay asynchronous notification URL to `https://lynshen.org/api/store/callbacks/{channel_id}`. Replace `{channel_id}` with the Alipay Channel ID.

Save the Alipay App ID, seller ID, merchant private key, Alipay public key, and environment in Store Management. Monoize verifies RSA2 and returns `success` only after it stores the verified event.

## Configure WeChat Pay callbacks

Set the WeChat Pay notification URL to `https://lynshen.org/api/store/callbacks/{channel_id}`. Replace `{channel_id}` with the WeChat Pay Channel ID.

Save the merchant ID, App ID, API v3 key, merchant certificate serial, merchant private key, platform certificate serial, and platform public key. Monoize verifies the platform signature and decrypts each payment resource before fulfillment.

## Buy a plan

Select a plan and a payment Channel. Each plan can apply several quota windows at the same time. A window can use 5 hours, 12 hours, a day, a week, a month, or a custom whole-hour duration.

Monoize stores plan quotas in CNY. The Store shows each quota as a rounded whole CNY or USD amount.

## Qualify SQLite for plans

Stop the Monoize application before you change the SQLite quota Gate. Set `MONOIZE_DATABASE_DSN` to the target SQLite database.

Import a passed drill manifest into the `next` slot:

```bash
monoize-store-ops quota-gate import --slot next --manifest ./quota-manifest.json
```

Read the compatibility fingerprint from the command output. Promote the imported manifest before you start the new application version:

```bash
monoize-store-ops quota-gate promote --expected-fingerprint <fingerprint>
```

The command rejects PostgreSQL, an oversized manifest, invalid JSON, and a manifest that does not match the live SQLite environment.

## Redeem a code

Enter one unused code in **Redeem code**. A code grants balance or activates a plan. Redemption does not use a payment Channel and does not create an order.

## Manage the Store

Administrators open `/dashboard/store-admin`. Use its four tabs to manage products, payment Channels, orders, and redemption codes.

- Set separate custom recharge limits for CNY and USD.
- Add an Alipay, WeChat Pay, Stripe, or draft HTTP Channel. Use a built-in icon, an HTTPS image URL, or an uploaded image.
- Open an existing official Channel. Enter every credential field and your current Admin password. Select **Replace credential**. Monoize encrypts the new version, retires the prior version, and disables the Channel.
- Keep an HTTP Channel disabled in Milestone 1.
- Review payment state and fulfillment state separately. Do not use a manual completion action.
- Generate 1 through 20 single-use codes. Copy the plaintext codes when Monoize shows them.
- Open **Privacy records** and **Retention** from the **Payment Channels** tab header.
- Select the shield action on an Alipay, WeChat Pay, or Stripe Channel row to open **Channel readiness**. An HTTP Channel row does not show that action.

## Review privacy records

Production checkout and callbacks require a current accepted Store privacy record. The review interval must not exceed 365 days.

Open **Store Management** at `/dashboard/store-admin`. Select the **Payment Channels** tab. Select **Privacy records**.

Each listed record shows policy version, jurisdiction, allowed regions, acceptance state, and next review date. A saved record cannot be edited.

Append a record when you approve a policy update. Enter these values, then select **Add privacy record**:

| Field | Accepted value |
| --- | --- |
| **Policy version** | 1 through 64 bytes |
| **Jurisdiction** | 1 through 128 bytes |
| **Allowed regions (comma-separated)** | 1 through 32 unique values |
| **Legal basis** | 1 through 512 bytes |
| **Evidence SHA-256 digest** | exactly 64 lowercase hexadecimal characters |
| **Financial record retention (days)** | 1 through 36500 |
| **Expired grant retention (hours)** | 1 through 24 |
| **Review after (days)** | 1 through 365 |

Monoize sets the reviewer, the approval time, and the next review date. Monoize also fixes three retention periods that the form does not expose: callback bodies 30 days, network metadata 90 days, and redemption audits 730 days.

## Bind Channel readiness

A Channel stays unavailable until its readiness profile references a current accepted privacy record.

Select the shield action on an Alipay, WeChat Pay, or Stripe Channel row. Select a **Privacy record**. Set **Callback verification passed** only after the signed callback test passes. Set the supported currencies, the checkout actions, the amount range for each currency, the license, runtime, and availability evidence digests, and a validity period of 1 through 90 days. Select **Save**.

The save action stays disabled while no privacy record exists. Add a record in **Privacy records** first.

Each Channel row shows a configured state and an effective state. An unavailable Channel lists its reason codes, such as `privacy_gate_pending`, `readiness_profile_missing`, `readiness_profile_expired`, `callback_verification_pending`, `compliance_missing`, and `capability_<kind>_missing`.

Payment terms confirmation and merchant capability records have no dialog. Use these Admin endpoints:

- `PUT /api/dashboard/store/admin/payment-channels/{id}/compliance` confirms the current Store payment terms. It requires a five-minute reauthentication grant with scope `compliance_confirm`.
- `PUT /api/dashboard/store/admin/payment-channels/{id}/capabilities/{capability}` records one merchant capability with a state, an environment, a provider product, an evidence digest, and an expiry.

## Understand data retention

Monoize runs one bounded retention job on the Store Primary at 03:00 UTC each day. A Replica does not run the job. Each run uses the accepted privacy record that is current when the run starts.

These retention periods apply to every record:

- Raw callback bodies: 30 days.
- Network metadata (source IP and User-Agent): 90 days.
- Redemption reveal, copy, and export audits: 730 days.
- Expired reauthentication grant hashes: the **Expired grant retention (hours)** value after expiry.
- Financial records: the **Financial record retention (days)** value. Use 2555 days for the seven-year default.

One run inspects and mutates at most 500 unheld root records in each of the five data classes: `raw_callback_bodies`, `network_metadata`, `financial_records`, `redemption_audits`, and `expired_reauth_grants`. Deleting one financial root record also deletes its payment attempts, event applications, refunds, refund-query retries, reward-recovery rows, and recovery-claim rows. The run keeps active entitlements and their generation records.

Each run runs in one transaction. A failure rolls back every deletion in that run. Repeating a run against unchanged data changes no already cleared field and does not fail because an earlier run deleted a candidate.

Payment data, callback evidence, backups, logs, and encryption keys stay inside the allowed regions of the privacy record. Every evidence read, export, retention override, and legal-hold operation writes an immutable access audit that records actor, role, scope, reason, time, and result.

## Run retention manually

Open **Store Management**. Select the **Payment Channels** tab. Select **Retention**.

The dialog shows the consecutive failure count, the checkout state (**Open** or **Paused**), the retention run count, and the legal hold count.

Enter your **Current password** and a **Reason**. Select **Run retention**. Monoize obtains a five-minute reauthentication grant with scope `retention_operation` and starts one bounded run.

A run that is already active returns HTTP `409` with code `retention_run_active`. A succeeded run sets the consecutive failure count to zero. A failed or interrupted run increments that count.

## Apply legal holds

A legal hold suspends deletion for listed identifiers in one data class. The **Retention** dialog shows the hold count. It does not create holds.

Create a hold with `POST /api/dashboard/store/admin/retention/legal-holds`. The request requires an Admin session, a Store Primary, and a five-minute reauthentication grant with scope `legal_hold`. The JSON body must contain `data_class`, `identifiers`, `reason`, `requesting_authority`, `requester_id`, `approver_role`, `expires_at`, and `extends_hold_id`.

- `data_class` must be one of the five retention data classes.
- `identifiers` must contain 1 through 100 distinct values. Each value holds at most 255 bytes.
- `approver_role` must be `privacy` or `legal`.
- `requester_id` must differ from the authenticated Admin. That Admin is the approver.
- `expires_at` must be a future RFC3339 instant.
- `extends_hold_id` must be `null` for an initial approval. An extension must reference a hold with the same data class and identifiers, and must use a later expiry.

A hold applies while its start time is at or before the evaluation time and the evaluation time is before its expiry. Expiry stops the hold and needs no operation. A hold never restores deleted data. No operation updates, deletes, reactivates, or extends a stored hold row. An extension inserts a new hold and a new approval audit.

## Clear a checkout pause

When a failed run makes the consecutive failure count reach three, and checkout is not already paused, Monoize creates one critical retention alert and pauses checkout.

While checkout is paused, a new order or a new payment attempt returns HTTP `503` with code `store_retention_paused`. An idempotent replay of an existing order or a terminal payment attempt can still return its earlier result. Callback ingestion, reconciliation, refunds, and retention operations stay available.

An application restart preserves the counter, the alert, and the pause. A succeeded run alone does not clear the pause.

Open **Retention** to clear the pause. The dialog shows the **Evidence SHA-256 digest** field only while checkout is paused. Enter your **Current password**, a **Reason**, and the digest. Select **Contain alert**.

Monoize records the containment, marks the alert contained, and resumes checkout. Containment does not change the consecutive failure count. A later failed run can pause checkout again. A containment request with no active uncontained alert returns HTTP `409` with code `retention_containment_unavailable`.
